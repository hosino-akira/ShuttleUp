# ShuttleUp 要件定義

更新日：2026-10-14。現在のリポジトリと設定を基準とする。「現行仕様」「改善案」「決定待ち」を区別し、未実行の検証は成功として記載しない。

## 目的と利用者

バドミントン・フィジカルトレーニングを個人が記録し、基本統計・期間分析・森林表示から継続状況を確認する。日本でのエンジニア転職活動向けポートフォリオ。現行の利用者区分は未認証利用者と認証済み本人。管理者用画面・役割別RBACは提供しない。

## 業務ルール

| ID | 対象 | ルール |
|---|---|---|
| BR-001 | 所有者 | userId／資源IDの指定だけでは権限を得ない。本人以外の資源は拒否。 |
| BR-002 | 共通種目 | 共通プリセットはsystemPreset=true、user_id=NULL。変更・削除を403で拒否。 |
| BR-003 | 独自種目 | 本人のuser_id、systemPreset=false。本人だけが利用できる。 |
| BR-004 | 森林 | 1保存済みセッション=1株。未来日は未表示。日付判定は読込時の端末ローカル日。 |
| BR-005 | 植物 | 6種。新規省略・旧NULLはcedar、更新時の省略は保存値保持。 |
| BR-006 | 試合日 | matchesにmatch_date物理列なし。親training_dateから応答生成。 |
| BR-007 | 試合得点 | 両方／片方の欠損は許可。同点は拒否。DB物理列はNULL可。 |
| BR-008 | 勝率 | Dashboardは欠損得点も試合数に含む。Pythonは欠損・同点を除外。分母を区別する。 |
| BR-009 | 連続日数 | 森は当日未実施なら昨日から。分析は期間終了日toから、to未実施なら0。 |
| BR-010 | 削除 | 物理削除。明細／試合の自動削除なし。参照制約409となり得る。 |
| BR-011 | 保存単位 | 基本情報・明細・試合は独立したAPI保存。基本情報のキャンセルで他の保存を戻さない。 |
| BR-012 | 相手名 | 同一ユーザー内同名をServiceで拒否。DB複合UK指定なし。 |
| BR-013 | 分析データ | FastAPIはHTTPで取得して計算し、MySQLへ直接接続・永続化しない。 |
| BR-014 | 率と空値 | 率は0～100%・小数1桁。未算出率null、空一覧[]。0と未入力を区別。 |

| ID | 対象 | 現状 | 対応 | 状態 |
|---|---|---|---|---|
| ISS-001 | フロントビルド | 未使用GlobalOutlined／BellOutlinedでTS6133。 | リリース前に使用／削除を判断してnpm run build再実行。 | 未解決 |

| ISS-003 | 文字数 | セッション／明細メモ・種目名のAPI@Sizeなし。 | 画面／DBとAPIの境界を揃えるか決定。 | 改善案 |

| ISS-005 | DB運用 | prodの接続値空欄、ddl-auto=update、SQL表示あり。 | 外部設定・最小権限・DDL管理・ログ方針を決定して検証。 | 本番決定待ち |
| ISS-006 | 分析転送 | AD-001のplantTypeフィールドはマッピング未設定。 | 森林表示用TS APIと区別。利用追加時にマッピング・テストを改訂。 | 確認済み |

性能目標、対応ブラウザー、RTO/RPO、保存期限、担当者は本番開始前に決定する。通信タイムアウトを応答時間SLOに読み替えない。決定待ちは性能合格・運用完了を意味しない。
