# 1. プロジェクト概要

## 1.1 プロジェクト名

```text
ShuttleUp
```

## 1.2 目的

ShuttleUp は、バドミントンのトレーニング内容や試合結果を記録・分析するための個人向けトレーニング管理アプリケーションである。

主な目的は次のとおり。

- トレーニング履歴の記録
- 種目別の実績管理
- 試合結果の記録
- 対戦相手の管理
- Dashboard によるデータ可視化
- 日本での IT 転職活動に利用できるポートフォリオの作成

## 1.3 将来的な拡張候補

- AI によるトレーニング分析
- トレーニングメニューの自動提案
- 試合傾向の分析
- 動画 URL と試合記録の連携
- Python によるデータ分析
- 認証・認可
- クラウド環境へのデプロイ
- モバイル対応

# 2. 全体アーキテクチャ

現在の構成は、フロントエンドとバックエンドを分離した構成である。

```text
Vue フロントエンド
        ↓ HTTP / JSON
Spring Boot REST API
        ↓ Spring Data JPA / Hibernate
MySQL
```

## 2.1 フロントエンドの責務

- 画面表示
- ユーザー操作の受付
- 入力フォーム
- API 呼び出し
- Dashboard 表示
- エラー表示
- ルーティング

## 2.2 バックエンドの責務

- REST API の提供
- 入力値の検証
- ビジネスロジック
- データベースアクセス
- Entity と DTO の変換
- JSON レスポンスの返却
- 例外処理

## 2.3 データベースの責務

- トレーニング履歴の永続化
- 試合記録の永続化
- 外部キーによるデータ整合性の維持
- マスタデータの管理
- 検索や集計に必要なデータの保持

# 5. バックエンド環境

## 5.1 最初の状態

最初の `backend` ディレクトリは、Entity の Java ファイルだけを置いた通常のフォルダであり、完全な Spring Boot プロジェクトではなかった。

不足していた主なファイル:

```text
pom.xml
mvnw
mvnw.cmd
.mvn/
src/main/resources/
BackendApplication.java
src/test/
```

## 5.2 対応方針

既存のディレクトリに手動で Maven や Spring Boot の設定ファイルを追加するのではなく、IntelliJ IDEA の Spring Boot 作成機能を使用して標準構成を生成した。

手順:

1. 既存の `backend` を `backend-old` に変更
2. Spring Initializr で新しい `backend` を作成
3. `backend-old` の `entity` を新しい `backend` に移動
4. 動作確認後に旧ディレクトリを削除

## 5.3 Spring Boot プロジェクト作成時の設定

```text
Name: backend
Group: com.shuttleup
Artifact: backend
Package: com.shuttleup.backend
Language: Java
Build System: Maven
Packaging: Jar
JDK: Microsoft OpenJDK 21
Java Version: 21
```

## 6.1 Spring Web

主な用途:

- REST API

主なアノテーション:

```java
@RestController
@RequestMapping
@GetMapping
@PostMapping
@PutMapping
@DeleteMapping
```

## 6.2 Spring Data JPA

主な用途:

- Entity とデータベース表の対応付け
- Repository による CRUD 操作
- SQL 記述量の削減
- Hibernate を介したデータベース操作

例:

```java
public interface TrainingSessionRepository
        extends JpaRepository<TrainingSession, Long> {

```

## 6.3 Validation

API の入力値を検証するために使用する。

主なアノテーション:

```java
@NotNull
@NotBlank
@Email
@Size
@Positive
```

例:

```java
@NotBlank
@Size(max = 100)
private String name;
```

### `@Column(nullable = false)` との違い

```java
@NotNull
```

- Java／API レベルの入力検証

```java
@Column(nullable = false)
```

- データベースの NOT NULL 制約

両方を設定することで、アプリケーション層とデータベース層の両方で整合性を保てる。

## 6.4 Lombok

重複しやすいコードを自動生成する。

主なアノテーション:

```java
@Getter
@Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
```

IntelliJ IDEA では Annotation Processing が有効になっているか確認する。

```text
Settings
→ Build, Execution, Deployment
→ Compiler
→ Annotation Processors
→ Enable annotation processing
```

## 6.5 MySQL Driver

# 10. Spring Data JPA とデータベースの関係

## 10.1 Spring Data JPA は SQLite 専用ではない

Spring Data JPA は特定のデータベース専用ではない。

一般的な構成:

```text
Spring Data JPA
    ↓
Hibernate
    ↓
JDBC Driver
    ↓
MySQL / PostgreSQL / H2 / Oracle / SQL Server など
```

それぞれの役割:

- Spring Data JPA: Repository と CRUD 操作を提供
- Hibernate: Entity 操作を SQL に変換
- JDBC Driver: Java と具体的な DB を接続
- Database: データを保存

## 10.2 JPA と JDBC Driver は別物

Spring Data JPA を追加しただけでは、接続先のデータベースは決まらない。

接続先は次の組み合わせで決まる。

1. どの JDBC Driver を追加したか
2. `application.properties` に何を設定したか

例:

```text
Spring Data JPA
+
MySQL Driver
+
MySQL 用接続 URL
=
MySQL を使用
```

## 10.3 SQLite を使用する場合

SQLite でも JPA を利用できるが、標準的な Spring Boot 構成より設定項目が増える場合がある。

必要になるものの例:

```text
Spring Data JPA
SQLite JDBC Driver
SQLite 対応 Hibernate Dialect
SQLite 用接続 URL
```

現在の ShuttleUp では SQLite を採用していない。

# 12. Entity 設計方針

## 12.1 基本方針

```text
Domain First
→ Entity
→ JPA
→ Database
```

業務モデルを先に考え、その後 Entity を設計し、JPA からデータベース表を生成する。

## 12.2 現在の Entity

```text
User
TrainingSession
TrainingRecord
ExerciseCategory
ExerciseType
Exercise
Opponent
Match
```

## 12.3 主な関係

```text
User
 └── TrainingSession
      ├── TrainingRecord
      └── Match
```

```text
ExerciseCategory
 └── ExerciseType
      └── Exercise
           └── TrainingRecord
```

```text
User
 └── Opponent
      └── Match
```

## 12.4 `Match.user` を削除した理由

`Match` は `TrainingSession` に所属し、`TrainingSession` は `User` に所属する。

そのため、ユーザーは次のように取得できる。

```java
match.getTrainingSession().getUser()
```

`Match` にも `user` を持たせると、次の二つが不一致になる可能性がある。

```text
Match.user
Match.trainingSession.user
```

重複した所有者情報を避けるため、`Match.user` は削除した。

## 12.5 `TrainingSession` と `TrainingRecord` を分ける理由

```text
TrainingSession
=
1 回のトレーニング全体
```

```text
TrainingRecord
=
その中で実施した個別種目
```

例:

```text
TrainingSession
2026-07-29
90 分

TrainingRecord
- スクワット
- ベンチプレス
- ランニング
```

# 13. コーディング規約

## 13.1 Java の命名規則

- クラス名: PascalCase
- プロパティ名: camelCase

例:

```java
TrainingSession
trainingDate
durationMinutes
createdAt
```

## 13.2 データベースの命名規則

- テーブル名: 複数形 + snake_case
- カラム名: snake_case
- 外部キー: `xxx_id`

例:

```text
training_sessions
training_records
training_date
duration_minutes
training_session_id
```

## 13.3 文字数制限

```text
name: length = 100
note: length = 1000
memo: length = 1000
```

例:

```java
@Column(nullable = false, length = 100)
private String name;
```

```java
@Column(length = 1000)
private String note;
```

## 13.4 非 NULL 制約

必須項目には次を設定する。

```java
@Column(nullable = false)
```

必須の外部キーには次を設定する。

```java
@JoinColumn(name = "training_session_id", nullable = false)
```

## 13.5 ID

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

`long` ではなく `Long` を使用する理由:

Entity がまだ保存されていない状態を、次のように表現できるため。

```java
id == null
```

## 13.6 作成日時・更新日時

主要 Entity には次を持たせる。

```java
createdAt
updatedAt
```

将来的には JPA Auditing の利用を検討する。

```java
@CreatedDate
@LastModifiedDate
@EnableJpaAuditing
```

# 15. 発生したエラーと解決方法

## 15.1 `mvn` が見つからない

エラー例:

```text
CommandNotFoundException
```

原因:

- Maven がグローバルインストールされていない
- 実行環境に `mvn` が存在しない

対応:

Maven Wrapper を使用する。

```powershell
.\mvnw.cmd clean compile
```

## 15.2 `Undefined module JDK`

意味:

- IntelliJ IDEA が、その Module に使用する JDK を認識していない

対応:

```text
File
→ Project Structure
→ Project
→ Project SDK
```

JDK 21 を選択する。

さらに:

```text
Modules
→ backend
→ Dependencies
→ Module SDK
```

`Project SDK` を選択する。

## 15.3 `java` コマンドが見つからない

エラー例:

```text
java is not recognized
```

原因:

- `JAVA_HOME` が未設定
- `Path` に `%JAVA_HOME%\bin` がない
- 設定後に PowerShell を再起動していない

対応:

```text
JAVA_HOME=C:\Users\27357\.jdks\ms-21.0.12
```

```text
Path に %JAVA_HOME%\bin を追加
```

## 15.4 Maven Wrapper が `JAVA_HOME` を認識しない

エラー例:

```text
The JAVA_HOME environment variable is not defined correctly
```

対応:

```powershell
echo $env:JAVA_HOME
```

確認後、正しい JDK ルートを設定する。

一時設定例:

```powershell
$env:JAVA_HOME="C:\Users\27357\.jdks\ms-21.0.12"
$env:Path="$env:JAVA_HOME\bin;$env:Path"
```

## 15.5 `BackendApplication.java` が見つからない

原因:

- Entity を移動する際に起動クラスを誤って削除した

対応:

`com.shuttleup.backend` 直下に再作成する。

## 15.6 DataSource の設定エラー

エラー例:

```text
Failed to configure a DataSource
'url' attribute is not specified
Failed to determine a suitable driver class
```

意味:

- Spring Boot は起動処理まで進んでいる
- Spring Data JPA と MySQL Driver が存在する
- ただし、データベース接続情報が未設定

必要な設定:

```properties
spring.datasource.url=
spring.datasource.username=
spring.datasource.password=
```

# 16. MySQL 接続設定

## 16.1 データベース作成例

```sql
CREATE DATABASE shuttleup
CHARACTER SET utf8mb4
COLLATE utf8mb4_unicode_ci;
```

## 16.2 `application.properties`

配置場所:

```text
src/main/resources/application.properties
```

ローカル開発用の例:

```properties
spring.datasource.url=jdbc:mysql://localhost:3306/shuttleup?useSSL=false&serverTimezone=Asia/Tokyo&characterEncoding=UTF-8
spring.datasource.username=root
spring.datasource.password=ローカルのパスワード

spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.properties.hibernate.format_sql=true
```

## 16.3 パスワード管理

データベースのパスワードを公開 GitHub に直接登録しない。

推奨例:

```properties
spring.datasource.username=${DB_USERNAME}
spring.datasource.password=${DB_PASSWORD}
```

Windows の環境変数や IDE の Run Configuration で設定する。

## 16.4 `ddl-auto`

主な値:

| 値 | 意味 |
|---|---|
| `none` | 自動変更しない |
| `validate` | Entity と DB の構造を検証 |
| `update` | 差分に応じて更新 |
| `create` | 起動時に作り直す |
| `create-drop` | 起動時に作成し、終了時に削除 |

開発初期は `update` を使えるが、本番環境では Flyway や Liquibase などのマイグレーションツールを利用する方が安全である。

## 21.2 既存の設計判断

### Spring Boot プロジェクトを作り直す

#### 背景

旧 `backend` は通常の Java フォルダであり、Maven・Spring Boot の標準構成がなかった。

#### 決定

Spring Initializr を使用して、新しい Spring Boot プロジェクトを作成した。

#### 理由

標準構成を手動で作るより安全であり、Maven Wrapper、起動クラス、resources、test などを漏れなく生成できるため。

---

### Java 21 を採用する

#### 決定

Microsoft OpenJDK 21 LTS を採用した。

#### 理由

LTS 版であり、新規 Spring Boot プロジェクトに適しているため。

---

### MySQL を採用する

#### 背景

初期段階では SQLite も候補として検討していた。

#### 決定

Spring Initializr で MySQL Driver を選択し、MySQL を採用した。

#### 理由

JPA、外部キー、インデックス、マイグレーション、デプロイなど、ポートフォリオとして説明できる要素が多いため。

---

### `Match.user` を削除する

#### 背景

`Match` は `TrainingSession` に所属し、`TrainingSession` は `User` に所属する。

#### 決定

`Match` から重複する `user` フィールドを削除した。

#### 理由

所有者情報の重複を避け、データの不整合を防ぐため。
